# Actual guarantees and limitations

Repository content and Git configuration are hostile data. No repository instructions are executed or treated as authority. Scan/audit do not run hooks, filters, external diffs/textconv, fsmonitor, submodule commands, package scripts, credential helpers, harnesses or lazy object fetches. Git commands use a trusted /usr/bin:/bin-resolved executable, an exact argument allowlist, stripped inherited environment, disabled optional locks/hooks/fsmonitor/maintenance/protocols and global/system configuration. Repository-selected external exclude files are disabled; exclusion evidence concerns approved repository ignore scopes, not unseen ambient/global patterns. Local include/includeIf sections fail closed before Git runs; without safe Git metadata the collector restricts itself to the declared known discovery surfaces rather than expanding ignored trees. Product worktrees resolve their real common directory; selected Git working roots are verified. No safe.directory wildcard or config rewrites.

Git inspection is tested against hostile configuration on the recorded Git version; no universal future-version guarantee. Bounded file reads avoid special files and final symlink following. Unapproved symlink attachment targets and linked/external companion Git metadata are not inspected; these layouts require future explicit metadata-root support. Parent-path races are detected where observed but same-user concurrent hostile replacement is not a security sandbox. Fresh scans retain private file/directory/config/index/HEAD/branch witnesses and recheck them after hosting collection and static evaluation, not merely at the end of local reads. Observed changes make the combined report unstable. This is not a transactional filesystem snapshot. Bounded static analysis can miss dynamic dependencies and excluded inputs. Linux was exercised; macOS not yet verified; native Windows unsupported.

The independent guard reports Git, working layout, active discovery/dependency and artifact checks separately. Exact product attachment index leaks remain visible even when ignored or companion content excluded. Product `.agents` packaging is positive-inclusion-based and tested with synthetic payloads. An ignored path is still readable; the rule is not secrecy. Never store auth, durable approvals or recovery preimages solely in the companion. Beware broad Git clean commands and wrong-repository Git actions inside .agents.

Only built-in plugins load in M1. Third-party installed entry points are metadata-only/untrusted, never imported automatically. In-process trusted Python plugins would not be hostile-code sandboxed. No semantic backend exists, no source text is submitted to an LLM. Manual guidance is advisory; it does not enforce human gates against a same-user process. No real harness configuration isolation or execution isolation is claimed.

GitHub requests go only to HTTPS api.github.com with production TLS verification, fixed endpoint construction, no redirects, approved-origin pagination, deadlines/body/page/record limits and at most three attempts. Authentication is only an explicitly named environment token, scoped to that origin. Remote comments/links are never fetch authority. 403/404/rate limits remain missing coverage, not absence. Ruleset visibility cannot prove all organisation/branch policies. Workflow runs preserve their commit/time but do not verify the current local checkout. API/provider may log reads.

Secret heuristics are conservative risk reduction, not proof of complete sanitisation. Recognised sensitive payloads/excerpts and their raw content/Git object identities are withheld; fingerprints exclude those withheld bytes and are not extraction preconditions. Inert credential-like product test data is redacted and informational, not treated as a live harness. Ordinary JSON/Markdown rendering escapes controls and untrusted formatting. Reports are private external files. Review before sharing; absolute machine paths are local provenance and no shareable-export scrubber exists yet. SQLite/blob hashes are integrity checks, not authenticity. Same-user code can rewrite local state. No human approvals can be created through bootstrap notes. Credentials are never stored by registration.

Back up external ledger and referenced blobs together using a quiescent consistent copy, plus bootstrap notes and any future attachment/recovery/parked material. M1 has no backup/prune automation. Blobs are persisted before database references; interrupted unreferenced blobs are retained, never opportunistically deleted. File permissions are restrictive on newly created state/report files; reused state parents require operator review. No guarantees for network filesystems/multi-host SQLite.
